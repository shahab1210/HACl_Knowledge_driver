# P7 — Embedding Layer

## 1. What Embeddings Are
An **embedding** is a dense numerical vector representation of text in a high-dimensional continuous space. Rather than relying on rigid keyword matching, embedding models project human language into vectors such that semantically similar concepts are located close to one another in vector space.

### Conceptual Workflow
```
Text:
"bearing overheating with increased vibration"
                  ↓
       Local Embedding Model
         (nomic-embed-text)
                  ↓
   [0.021, -0.184, 0.093, ... ]
```
This vector represents semantic information about the text. 

For example, the two statements:
- *"bearing temperature is increasing and vibration is elevated"*
- *"bearing overheating with abnormal mechanical vibration"*

use different phrasing and words, yet produce embedding vectors with very high cosine similarity because they describe the exact same physical failure state.

---

## 2. Why P_311 Needs Embeddings
The overarching objective of **P_311 (Knowledge-Driven IoT Fault Diagnosis Assistant)** is to diagnose machine failures from real-time IoT sensor telemetry (such as high vibration, elevated current, or pressure drop).

In operational plants:
- Maintenance inquiries and automated anomaly alerts rarely match exact keyword strings in manuals.
- A rule engine or operator might state: *"Motor draws 11A and casing is scorching hot"*.
- The knowledge base contains: `FAULT-003: Motor Overheating` and `FAULT-004: Motor Overcurrent`.
- Dense embeddings allow the diagnostic assistant to semantically match observed telemetry symptoms against the knowledge corpus, even when terminology varies.

---

## 3. Why a Local Embedding Model Is Used
- **Zero Cloud Leakage & Strict Privacy:** Industrial machinery specifications, telemetry patterns, plant schematics, and operational logs are proprietary and sensitive. No data is transmitted to external cloud APIs (e.g., OpenAI or Cohere).
- **Offline / On-Premise Resilience:** Manufacturing facilities, offshore platforms, and utility plants frequently operate in air-gapped or network-constrained environments. A local model ensures 100% offline availability.
- **Zero Subscription Costs & Unlimited Throughput:** Local processing eliminates API rate limits, per-token billing, and third-party vendor dependencies.

## 4. What Ollama Does in P7
**Ollama** acts as the high-performance local AI runtime serving the embedding model:
- Manages model lifecycle and weights (`nomic-embed-text`).
- Provides hardware-accelerated inference (leveraging Apple Silicon MLX / Metal GPU).
- Exposes local HTTP endpoints:
  - `POST /api/embed` (Standard modern batch/single embedding endpoint)
  - `POST /api/embeddings` (Legacy single-prompt endpoint)
  - `GET /api/tags` (Model catalog inspection)
  - `GET /api/version` (Server health check)

The P7 client (`client.py`) connects to `http://localhost:11434` without requiring external API keys.

## 5. Input from P6 (`ai/ingestion/output/chunks.json`)
P7 consumes the validated output generated by Phase 6:
```
P5 Knowledge Base (Markdown)
             ↓
P6 Document Ingestion (chunks.json)
             ↓
P7 Embedding Layer (embeddings.json)
```

P7 strictly reads `ai/ingestion/output/chunks.json` as its single source of truth. Every input chunk is validated against schema requirements:
- `chunk_id`
- `document_id`
- `document_type`
- `source`
- `chunk_index`
- `title`
- `text`
- Optional metadata: `category`, `equipment`, `severity`, `sensors`.

## 7. Dynamic Embedding Dimension
The embedding dimension is **never hard-coded**. The system dynamically detects the vector dimensionality directly from the active local model output:
- For `nomic-embed-text`: 768 dimensions.
- If an alternative model (e.g. `all-minilm` with 384 dimensions) is selected, P7 automatically detects and records the actual dimension.

---

## 8. Metadata Preservation
Every chunk's structural attributes (`chunk_id`, `document_id`, `document_type`, `category`, `equipment`, `severity`, `sensors`, `source`) are strictly preserved alongside the numerical vector. This enables **hybrid filtering** in Phase 8 (e.g., filtering vectors where `equipment == 'motor'` AND `sensors CONTAINS 'vibration'`).

## 10. Strict Phase Boundary (Why Vector DB Is Not Part of P7)
> [!IMPORTANT]
> **P7 is exclusively responsible for embedding computation and local serialization.**
>
> P7 does **NOT** implement:
> - Vector database installation or configuration (Chroma, FAISS, Qdrant, PGvector)
> - Vector indexing or similarity search (cosine, dot product, L2)
> - RAG prompt augmentation
> - LLM inference or fault diagnosis
> - Spring Boot or MQTT integration
>
> All vector indexing and similarity retrieval belongs strictly to **Phase 8 (P8 — Vector Database)**.

---

## 11. How P8 Will Consume `embeddings.json`
In Phase 8:
1. **P8 Loader:** Reads `ai/embeddings/output/embeddings.json`.
2. **Collection Initialization:** Creates a vector database collection configured with the recorded `embedding_dimension` (768).
3. **Record Insertion:** Stores each chunk's `embedding` vector as the primary key vector, attaching the chunk text and metadata (`category`, `equipment`, `severity`, `sensors`) as payload fields.
4. **Index Construction:** Builds an approximate nearest neighbor (ANN) index (e.g., HNSW) for sub-millisecond similarity queries.
